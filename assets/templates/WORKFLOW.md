# WORKFLOW —— 工作协议

> 任何 Agent 进入本项目后的标准工作方式。与 `USER_PROFILE.md` 配合使用：**WORKFLOW 定流程，USER_PROFILE 定风格**。
> 本文件与具体 AI 工具无关——ZCode、Codex、Claude、Gemini 进来，都按同一套协议干活。

## 一、开工（每次会话开始）

1. 按 `AGENTS.md` 的必读顺序读完 Relay 文件
2. 对照 `PROJECT_CONTEXT.md`（现状）与 `HANDOFF.md`（上次交接），理解项目当前状态
3. **先总结，再动手**：用自己的话向用户复述「项目现状 + 我理解的本任务」，等用户确认或给出指令后再改代码
4. 用户本次指令与文档记录的「下一步」冲突时：先说明差异，经用户确认再动手
5. 上下文被压缩 / 会话中断 / 自己「失忆」：立即重读 Relay 文件，一切以文档为准，禁止凭残存记忆继续操作

## 二、执行（改代码的边界）

- ❌ **不随意改变架构**：目录结构、技术选型、数据流不动，除非用户明确要求，且记入 `DECISIONS.md`
- ❌ **不删除已有功能**：哪怕看起来多余；觉得有问题就向用户提出，等用户决定
- ✅ **优先小范围修改**：一次只做一件事，验证通过再继续
- ✅ **保持已有设计语言**：命名、配色、组件写法、代码风格向现有代码看齐，不夹带个人偏好
- ✅ **用户的习惯优先**：自己的默认做法与 `USER_PROFILE.md` 冲突时，听用户的

## 三、收尾（每次会话结束，缺一不可）

1. 更新 `PROJECT_CONTEXT.md` —— 项目状态快照（现在时）
2. `HANDOFF.md` 顶部追加交接条目 —— 写给下一任的一封信
3. `CHANGELOG.md` 顶部追加变更条目 —— **必填执行 Agent（工具 + 模型）**
4. 重要设计选择 → `DECISIONS.md` 追加编号；阶段推进 → 更新 `ROADMAP.md`
5. git 提交并推送（规则见 `AGENTS.md`）—— 远端是唯一备份，不推送 = 工作只完成一半

**汇报四件套**（向用户输出改动的最低标准）：

| 输出 | 回答的问题 |
|---|---|
| 修改内容 | 改了什么 |
| 修改原因 | 为什么这么改 |
| 测试方式 | 怎么验证它是对的 |
| 下一步建议 | 接下来做什么 |

## 四、部署边界

- ⛔ **不主动部署、不主动发布**，除非用户明确要求——改完代码 ≠ 可以上线
- 部署类项目的日常链条（本地 → push → 自动部署）见 `AGENTS.md`
